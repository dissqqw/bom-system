## 2. Разделение BOM и маршрутной технологии

- `BOMPosition` — конструкторский/материальный состав: какое изделие из каких компонентов состоит.
- `ProductOperation` — технологическая позиция, описывающая состояние изделия после операции или приобретения.
- `InputResourcePosition` — связь между операцией-потребителем (`out_to_id`) и операцией-источником (`in_to_id`), включая норму расхода.

Таким образом, BOM и технологический граф хранятся отдельно, но используют общий справочник `Product` и единицы измерения `Unit`.

## 3. Реализация наследования

Использовано наследование SQLAlchemy с отдельными таблицами подклассов:

- `tm_product_operations` — общие поля `ProductOperation`;
- `tm_purchase_positions` — закупочная цена для `PurchasePosition`;
- `tm_route_positions` — время, ГРЦ, класс операции, профессия и квалификация для `RoutePosition`.

В `tm_product_operations.position_type` хранится тип позиции (`purchase` или `route`). Поэтому поиск по `ProductOperation` возвращает конкретный тип объекта.

## 4. Как задаётся технологический граф

Для последовательности операций одного изделия создаются несколько `RoutePosition` с разными `sequence_number`. Предшествующая операция указывается как источник входного ресурса следующей операции.

Например, если операция 020 выполняется после 010, создаётся связь:

```json
{
  "out_to_id": 102,
  "in_to_id": 101,
  "consumption": 1,
  "for_quantity": 1,
  "unit_id": 1
}
```

Здесь 102 — операция-потребитель 020, а 101 — результат операции-источника 010.

Для закупного материала создаётся `PurchasePosition`, после чего он указывается как `in_to_id` у операции, которая его расходует.

## 5. Расчётные функции

### FIND_TM(pIdEl)

1. Получает изделие по `pIdEl`.
2. Определяет конечные операции изделия: это операции, результаты которых не используются как входной ресурс другой операции того же изделия.
3. Обходит связи `InputResourcePosition` рекурсивно.
4. Проверяет наличие циклов.
5. Возвращает производственные позиции в технологическом порядке, а закупные позиции — отдельным списком.

### MR_Q(pIdTO, pQ)

1. Получает одну `RoutePosition` по `pIdTO`.
2. Берёт только непосредственные входные ресурсы данной операции.
3. Для каждого ресурса считает `pQ * consumption / for_quantity`.
4. Возвращает количество, единицу измерения и при наличии цену закупной позиции.

Функция не раскрывает вложенные операции. Для сводного расчёта служит `SUM_MR`.

### SUM_MR(pIdEl, pQ)

1. Определяет конечные операции заданного изделия.
2. Строит топологический план всех достижимых зависимостей.
3. Передаёт количество от операции-потребителя к операции-источнику с коэффициентом `consumption / for_quantity`.
4. Для `RoutePosition` продолжает обход по её входным ресурсам.
5. Для `PurchasePosition` добавляет ресурс в итоговую потребность.
6. Складывает одинаковые закупные ресурсы по изделию, единице измерения и цене.

Цена закупки берётся из `PurchasePosition.purchase_price`; если она не задана, используется `Product.price`.

### TR_TO(pIdEl, pQ)

1. Использует тот же граф и рассчитанное количество для каждой операции.
2. Для каждой `RoutePosition` вычисляет `setup_time + operation_quantity * unit_time`.
3. Группирует часы по профессии и квалификации.
4. Для денежной оценки умножает часы на `ProfessionClassifier.hourly_rate`.

В реализации `setup_time` и `unit_time` измеряются в часах. Подготовительно-заключительное время учитывается один раз на партию операции.

### CALCULATE_TM_COST(pIdEl, pQ)

Дополнительная функция для обязательной калькуляции себестоимости. Объединяет результат `SUM_MR` и `TR_TO`, выводит стоимость материалов, труда и общую стоимость. Если для хотя бы одного ресурса или профессии не задана цена/ставка, соответствующий итог возвращается как `null`, а не как неполная сумма.

## 6. Почему количество не хранится в Product

Количество выпускаемой партии — параметр конкретного расчёта, а не постоянное свойство изделия. Поэтому `pQ` передаётся в функции и API.

Норма на входной позиции может быть задана, например, как 6 деталей на 3 изделия. Тогда для 10 изделий требуется `10 * 6 / 3 = 20` деталей.

## 7. Поля, добавленные сверх исходного описания диаграммы

- `ProductOperation.product_id` — внешний ключ на изделие, без него невозможно определить маршрут конкретного изделия.
- `InputResourcePosition.unit_id` — внешний ключ на уже существующую таблицу `ei`.
- `RoutePosition.work_center_id`, `operation_class_id`, `profession_class_id` — связи с соответствующими справочниками.
- `ProfessionClassifier.hourly_rate` — ставка за час труда; нужна для денежной калькуляции трудовых затрат.
- `PurchasePosition.purchase_price` — цена позиции закупки; при отсутствии используется `Product.price`.

`WorkCenter.hourly_rate` сохранён как дополнительный тариф рабочего центра, но не включён в общую себестоимость: в задании отдельно запрошены стоимость материалов и стоимость труда. Его можно подключить отдельной составляющей, если преподаватель потребует учитывать стоимость эксплуатации оборудования.

## 8. Примеры запросов API

Создать ГРЦ:

```http
POST /api/tm/work-centers
Content-Type: application/json

{"name": "Шиномонтажный участок"}
```

Создать класс технологической операции:

```http
POST /api/tm/operation-classes
Content-Type: application/json

{"name": "Установка колёс"}
```

Создать профессию с тарифом:

```http
POST /api/tm/professions
Content-Type: application/json

{"name": "Автомеханик", "hourly_rate": 900}
```

Создать производственную операцию:

```http
POST /api/tm/route-positions
Content-Type: application/json

{
  "product_id": 8,
  "sequence_number": 10,
  "setup_time": 0.25,
  "unit_time": 0.5,
  "work_center_id": 1,
  "operation_class_id": 1,
  "profession_class_id": 1,
  "qualification": "Grade4"
}
```

Создать закупную позицию:

```http
POST /api/tm/purchase-positions
Content-Type: application/json

{
  "product_id": 4,
  "sequence_number": 1,
  "purchase_price": 5000
}
```

Добавить входной ресурс:

```http
POST /api/tm/input-resources
Content-Type: application/json

{
  "out_to_id": 10,
  "in_to_id": 11,
  "consumption": 4,
  "for_quantity": 1,
  "unit_id": 1
}
```

Добавить инструмент/оснастку:

```http
POST /api/tm/tool-requirements
Content-Type: application/json

{
  "route_position_id": 10,
  "product_id": 6,
  "quantity": 1
}
```

Выполнить расчёты для 10 изделий:

```http
GET /api/tm/product/8/route
GET /api/tm/operation/10/resources?quantity=10
GET /api/tm/product/8/materials?quantity=10
GET /api/tm/product/8/labor?quantity=10
GET /api/tm/product/8/cost?quantity=10
```

ID в примерах условные: для реальных запросов подставляются ID, полученные при создании справочников и технологических позиций.

## 9. Обновление SQLite-базы

В `bom/app.py` новые модели импортируются до вызова `db.create_all()`. При запуске:

```bash
python -m bom.app
```

SQLite создаст отсутствующие таблицы маршрутной технологии в существующей `bom/instance/bom_database.db`. Новые поля в существующих таблицах не добавлялись, поэтому миграция старых таблиц не требуется.

## 10. Важное ограничение по формулировке «хранимые функции»

В текущем проекте используется SQLite. SQLite не поддерживает хранимые процедуры и функции PL/pgSQL как PostgreSQL. `FIND_TM`, `MR_Q`, `SUM_MR`, `TR_TO` в этом решении — функции Python-сервисного слоя, работающие через SQLAlchemy и вызываемые через Flask API.

Если по методическим требованиям нужны именно хранимые функции внутри СУБД, базу следует перевести на PostgreSQL и реализовать алгоритмы отдельными SQL/PLpgSQL-функциями. Называть текущую реализацию хранимыми функциями SQLite было бы технически неверно.
